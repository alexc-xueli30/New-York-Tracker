# Design: Geographic Grid Sampling for 311 Map Dot Distribution

## Problem Statement

`fetchRecentComplaints()` in `lib/311-api.ts` runs a single Socrata query ordered by
`created_date DESC` with a `$limit` of 60. This returns the 60 most recent open
complaints across all of NYC -- which cluster in whichever neighborhoods happen to be
filing the most complaints that day. The result: Manhattan and Central Brooklyn fill
with dots while the Bronx, Queens outer edges, and Staten Island appear nearly empty.
The map looks broken, not like a living picture of NYC's civic pulse.

## What Makes This Cool

A map where every borough shows up. When dots appear in Far Rockaway, Throgs Neck,
and Tottenville alongside Midtown, the user feels the full geography of the city's
problems. The map becomes a genuine NYC dashboard, not a Manhattan tracker.

## Constraints

- Socrata API rate limit: unauthenticated ~1k req/hr shared IP; with app token much higher.
- Response time budget: initial load should feel fast (<2s). 20 parallel fetches
  are fine since Socrata's CDN handles parallel well and each cell returns 6 records.
- Next.js ISR cache at 1800s already handles repeat loads.
- Must not break the existing MapSighting[] type or viewport-based refetch on pan/zoom.

## Premises

1. The root cause is temporal ordering -- "most recent" means "wherever people are
   filing complaints today," not "all of NYC." Confirmed.
2. A 4x5 geographic grid (20 cells x 6 records = 120 max) is the right spatial
   distribution strategy. Confirmed.
3. 20 parallel Socrata fetches are acceptable -- fast, cached, and bounded. Confirmed.
4. Deduplication by unique_key handles records near cell boundaries. Confirmed.

## Approaches Considered

### Approach A: Geographic Grid -- 20 Cells x 6 Records (recommended)

Split NYC bounds (lat 40.48-40.92, lng -74.27 to -73.70) into a 4x5 grid.
Fire 20 parallel Socrata queries, each with a bounding-box $where using the
latitude/longitude range form (matching the existing code style):
  `latitude BETWEEN 40.48 AND 40.59 AND longitude BETWEEN -74.27 AND -74.156`
Each cell gets `$limit: 6` and `$order: created_date DESC`. Each fetch is passed
`{ next: { revalidate: 1800 } }` -- the same ISR cache tag as the current single
query -- so the 20 parallel fetches are each cached independently by Next.js;
repeat page loads hit the cache, not the Socrata API.
Deduplicate results by unique_key. Returns up to 120 unique records spanning all
of NYC. Empty cells (water, parks with no complaints) return [] and are dropped.
The UI renders whatever count is returned; the caller should expect a variable
total of up to 120 rather than a fixed count.

### Approach B: Borough-Based Sampling -- 5 Queries x 12 Records

One query per borough using the borough field, LIMIT 12 each = 60 total.
Simpler (5 calls), but within-borough clustering persists. Bronx and Staten Island
residents filing fewer complaints means those boroughs still look sparse in their
outer neighborhoods.

### Approach C: Single Large Query + Random Subsample

Fetch 200 records from last 30 days, accept whatever random geographic distribution
falls out. Socrata's $order=random() is unreliable and slow at this scale.
Active areas still dominate. Rejected.

## Recommended Approach

Approach A: Geographic grid.

It's the only approach that guarantees spatial distribution regardless of where
complaints are being filed that day. Borough-based sampling (B) still suffers
the same root-cause bias (temporal ordering) at a finer geographic level.

Implementation: replace the single socrataUrl() call in fetchRecentComplaints()
with a Promise.all over a statically-defined grid.

## Open Questions

- Should each cell return 6 or 8 records? 6 x 20 = 120 feels right for zoom 11.
  8 x 20 = 160 may cluster visually at zoom 10. Start with 6; tune after visual check.

Decided: empty cells (water-only areas, large parks) return [] and are dropped silently.

## Success Criteria

1. Map loads with dots visible in complaint-generating areas of all 5 boroughs
   (inner neighborhoods of each borough; outer/remote areas may remain empty if
   no complaints were filed there recently -- that's correct behavior, not a bug).
2. No single borough visually dominates at default zoom 11.
3. Initial load time remains under 2 seconds (DevTools network tab).
4. All existing MapSighting type contracts maintained -- no TypeScript errors.

## Distribution Plan

Existing Vercel deployment pipeline covers this. No new infrastructure.
